# Statamic roles and groups

Create and change user roles, user groups and their permissions **the way this
project already does it**. A wrong permission locks people out or gives them
too much access, so plan first and verify after.

The references this skill needs are inlined at the end of this file
(**Inlined references**).

## Workflow

### 1. Detect

- Follow **Project detection** (inlined below) for the Statamic version and
  moved paths.
- Read `config/statamic/users.php` (repository, role/group paths, new-user
  defaults), `roles.yaml`, `groups.yaml`, and list the handles of every
  collection, navigation, global set, taxonomy, asset container and form.

**Stop condition — database.** Roles or groups are in the database only when
`repository` is `eloquent` **and** `tables.roles` / `tables.groups` in
`config/statamic/users.php` name a table (not `false`). Then change **no files
for that part by any tool**; point to the Control Panel. An `eloquent` user
repository with `tables.roles => false` still keeps roles in `roles.yaml` —
edit the YAML as usual.

### 2. Stop on real ambiguity

Ask, naming the options, and change no files (by any tool) until answered, when:

- The request names something that does not exist ("the news section" with no
  `news` collection). List what does exist; never invent a handle.
- The requested role or group handle already exists — offer to extend it.
- The scope is unclear ("can manage the blog": view/edit only, or also create,
  publish, delete?). Propose a default.

A pre-approved plan does not clear real ambiguity.

### 3. Present the plan — hard gate

Present, before any edit: the file(s), the exact YAML, and for each role the
full permission list **with what it still cannot do**. Then **stop and wait for
approval — no Write, Edit or Bash writes in the same turn** unless the request
explicitly pre-approves it ("I approve your plan in advance").

### 4. Write

Minimal edits; keep order, quote style and comments. Permission strings,
hierarchy and file shapes: **Roles, groups and permissions** below.

### 5. Verify

- The file parses (PHP with `vendor/autoload.php` and
  `Symfony\Component\Yaml\Yaml::parseFile()`, else `ruby -ryaml`, else `python3`
  with `yaml`).
- Every permission matches a string in **Permission strings** below with a real
  handle, and every child has all its parents plus `access cp`. Every role a
  group lists exists.
- Runtime, when `php` and `vendor/` exist (read-only):
  `php artisan tinker --execute='echo implode(",", \Statamic\Facades\Role::find("<handle>")->permissions()->all());'`.
  If it cannot run, report **"runtime check not run"** and why.

A failed check: show it, fix it, re-verify. Then summarise what changed and
remind the user to assign the role or group to users in the Control Panel.

## Out of scope

Creating or editing users themselves, passwords, and the user blueprint.

### Project detection

Establish all of the following before planning. Report anything uncertain
instead of guessing.

#### 1. Statamic version

- Read `composer.lock` → package `statamic/cms` → `version`.
- No lock file: read `composer.json` → `require["statamic/cms"]` and state that
  the constraint is used, not the installed version.
- Neither mentions `statamic/cms`: this may not be a Statamic project — ask.

#### 2. Storage driver (stop condition)

- `statamic/eloquent-driver` installed (lock or `composer.json`) **and**
  `config/statamic/eloquent-driver.php` sets `'driver' => 'eloquent'` under
  `blueprints`, `fieldsets`, `collections` or `taxonomies` → that structure lives
  in the database. Stop (see SKILL.md step 1); write nothing at all.
- Driver installed but only `entries`/`terms`/other content types on `eloquent`
  → blueprints are still files. Continue, and mention it in the plan.

#### 3. Paths

| What | Default location |
|---|---|
| Collection blueprints | `resources/blueprints/collections/<collection>/<blueprint>.yaml` |
| Taxonomy (term) blueprints | `resources/blueprints/taxonomies/<taxonomy>/<blueprint>.yaml` |
| Globals / forms / assets / user blueprints | `resources/blueprints/globals/`, `forms/`, `assets/`, `user.yaml` |
| Fieldsets | `resources/fieldsets/<handle>.yaml` |
| Collection config | `content/collections/<handle>.yaml` |
| Taxonomy config | `content/taxonomies/<handle>.yaml` |
| Navigation config / tree / blueprint | `content/navigation/<handle>.yaml` / `content/trees/navigation/<handle>.yaml` / `resources/blueprints/navigation/<handle>.yaml` (see **Navigation**) |
| Form config / blueprint | `resources/forms/<handle>.yaml` / `resources/blueprints/forms/<handle>.yaml` (forms skill) |
| Asset container config / blueprint | `content/assets/<handle>.yaml` / `resources/blueprints/assets/<handle>.yaml`; its disk in `config/filesystems.php` |
| Global set config / values | `content/globals/<handle>.yaml` / `content/globals/<site>/<handle>.yaml` (see **Globals**) |

These are only defaults. **Always** check the config, even when the default
directories exist (a fresh install leaves `resources/blueprints/user.yaml` and
`default.yaml` behind after the paths are moved):

| Config | Key | Moves |
|---|---|---|
| `config/statamic/system.php` | `blueprints_path` (string, or per-type array like `['default' => …, 'forms' => …]`) | Blueprints |
| `config/statamic/system.php` | `fieldsets_path` | Fieldsets |
| `config/statamic/stache.php` | `stores.collections.directory` | Collection configs (entries live under `stores.entries.directory`) |
| `config/statamic/stache.php` | `stores.taxonomies.directory` | Taxonomy configs |
| `config/statamic/stache.php` | `stores.navigation.directory`, `stores.nav-trees.directory` | Navigation configs and trees |
| `config/statamic/forms.php` | `forms` | Form configs |
| `config/statamic/stache.php` | `stores.asset-containers.directory` | Asset container configs |
| `config/statamic/stache.php` | `stores.globals.directory`, `stores.global-variables.directory` | Global set configs and values |

Resolve `base_path(...)` / `resource_path(...)` to project-relative paths and use
those for every read and write. Mention moved paths in the plan.
- A collection uses a taxonomy via `taxonomies: [<handle>]` in its collection
  config; entries link terms with a `terms` field.

#### 4. Page builders

- Grep blueprints and fieldsets for `type: replicator` and `type: bard` fields
  that have `sets:`.
- Record for each: file, field handle, tab, **inline** (in a blueprint) or
  **fieldset** (pulled into blueprints with `- import: <fieldset>`), the set
  groups (`sets: <group>: { display, sets: … }`) and the sets in each.
- A fieldset-based builder is edited **in the fieldset**, never by copying sets
  into a blueprint.
- More than one candidate → stop and ask (SKILL.md step 2).

#### 5. Template dispatch

Find where the builder field is rendered, to learn the template language and the
path a new partial needs:

- **Antlers:** `{{ <field> }} … {{ partial src="<dir>/{type}" }} … {{ /<field> }}`
  → partials at `resources/views/<dir>/<set>.antlers.html`.
- **Blade:** a loop over the field rendering
  `<x-dynamic-component :component="'<prefix>.'.$block['type']" …>`
  → anonymous components at `resources/views/components/<prefix>/<set>.blade.php`
  (dots in the prefix are directories).
- Anything else (`@include("blocks.{$type}")`, a custom tag, a view composer):
  describe it in the plan and follow it, or ask if unclear.

The template language is that of the dispatching template and the sibling
partials, not a guess from the file tree.

#### 6. Conventions

- **CP label language:** read existing `display:` values. New labels use that
  language **regardless of the language of the user's request**.
- **Handles:** match existing style (Statamic's norm is snake_case).
- **Set metadata:** add `icon:` / `instructions:` only if sibling sets have them.
- **Ordering:** obey rules stated in YAML comments (e.g. "keep sets alphabetical");
  otherwise append at the end of the group.
- **Closest sibling partial:** note its wrapper element, empty-field guards and
  comment style; the new partial copies them.
- **Existing handles:** if the requested set or field handle already exists, say
  so and offer to extend it.

### Roles, groups and permissions

| Part | Default path | Shape |
|---|---|---|
| Roles | `resources/users/roles.yaml` | map: `<handle>: { title, permissions: [..] }` |
| Groups | `resources/users/groups.yaml` | map: `<handle>: { title, roles: [<role handle>, ..] }` |
| Defaults for new users | `config/statamic/users.php` | `new_user_roles`, `new_user_groups` |

The paths move via `repositories.file.paths.roles` / `.groups` in
`config/statamic/users.php`. Roles/groups move to the database only when
`repository` is `eloquent` and `tables.roles` / `tables.groups` is a table name;
with `false` (the default) they stay in the YAML files even though users are in
the database.

`super` grants everything. Never add it unless the user asks for a super admin.

#### Permission strings

Use Statamic's exact wording; `{x}` is an existing handle. Indentation is the
hierarchy: **a child only works when every parent above it is also granted**,
and nothing works without `access cp`.

```
access cp
configure sites | configure fields | configure form fields | manage preferences
access {site} site                         (multisite only)
configure collections
view {collection} entries
  edit {collection} entries
    create {collection} entries
    delete {collection} entries
    publish {collection} entries
    reorder {collection} entries
    edit other authors {collection} entries
      publish other authors {collection} entries
      delete other authors {collection} entries
configure navs
view {nav} nav
  edit {nav} nav
configure globals
edit {global} globals
configure taxonomies
view {taxonomy} terms
  edit {taxonomy} terms
    create {taxonomy} terms
    delete {taxonomy} terms
configure asset containers
view {container} assets
  upload {container} assets
  edit {container} folders
  edit {container} assets
    move {container} assets
    rename {container} assets
    delete {container} assets
view users
  edit users
    create users
    delete users
    change passwords
    assign user groups
    assign roles
edit user groups
edit roles
impersonate users
configure forms
view {form} form submissions
  delete {form} form submissions
view updates | configure addons
```

Handles come from the project: collections `content/collections/*.yaml`, navs
`content/navigation/*.yaml`, globals `content/globals/*.yaml`, taxonomies
`content/taxonomies/*.yaml`, asset containers `content/assets/*.yaml`, forms
`resources/forms/*.yaml` (honour moved paths, see project-detection).

#### Writing

- Mirror the file: quote style (`'access cp'`), order, comments.
- A role "that can do X but not Y": grant X with all its parents; leave Y and
  its children out; mention what the role still cannot do.
- Groups list role handles that exist in `roles.yaml`.
- A commented-out example block may be replaced by the first real entry.
